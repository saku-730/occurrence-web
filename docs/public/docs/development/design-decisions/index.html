Design Decisions

  • Open in ChatGPT
  • Open in Claude
  • Open in Perplexity
  • Copy Markdown

このページでは、Bio Databaseにおける主要な設計判断を記録します。利用手順ではなく、技術選定の背景とトレードオフを説明するためのページです。

RDFとPostgreSQLを併用した理由#

課題#

オカレンスは柔軟な語彙と多様な関係を必要とする一方、ユーザー、セッション、認証トークン、メディアメタデータには整合性の高い更新と検索が必要です。

候補#

  • すべてをRDFストアで管理する
  • すべてをリレーショナルデータベースで管理する
  • RDFとPostgreSQLを用途別に併用する

採用した方法#

オカレンスと語彙・分類群はRDFとしてFusekiに保存し、ユーザー・認証・セッション・メディアメタデータはPostgreSQLで管理します。

採用理由#

RDFは外部語彙と関係の追加に適し、PostgreSQLは認証やトランザクションを伴うアプリケーションデータに適しています。

欠点#

データが2つのストアに分かれるため、横断処理と障害時の整合性を考慮する必要があります。

今後の改善#

ストア間の補償処理、監査ログ、孤立メディア検出を強化します。

FusekiをDockerで運用する理由#

課題#

RDFストアを開発環境と本番環境で同じ構成に保ち、設定とデータ保存先を明確にする必要があります。

候補#

  • ホストOSへ直接インストールする
  • FusekiをDockerコンテナとして運用する
  • 外部のマネージドRDFサービスを利用する

採用した方法#

FusekiをDockerで運用します。

採用理由#

バージョン、Java実行環境、起動設定をコンテナへ閉じ込められ、環境差分を抑えられます。

欠点#

永続ボリューム、バックアップ、コンテナ監視を別途運用する必要があります。

今後の改善#

バックアップ手順、リストア手順、ヘルスチェック、更新手順を自動化します。

MinIOではなくGarageを選んだ理由#

課題#

添付ファイルをS3互換APIで保存しつつ、セルフホスト環境で運用したい必要があります。

候補#

  • MinIO
  • Garage
  • クラウドのオブジェクトストレージ

採用した方法#

S3互換オブジェクトストレージとしてGarageを採用します。

採用理由#

Garageは軽量なセルフホスト運用を前提とし、S3互換APIを提供します。バックエンドはS3互換の境界を通じてファイルを扱えます。

欠点#

MinIOと比べると、運用事例や周辺ツールの選択肢が限られる場合があります。

今後の改善#

バックアップ、容量監視、障害復旧の運用手順を整備します。

GBIF APIだけでなくBackbone全体を取り込んだ理由#

課題#

分類候補の表示だけでなく、親子関係、シノニム、受容名を使った検索をアプリケーション内で安定して行う必要があります。

候補#

  • GBIF APIだけを都度呼び出す
  • GBIF Backbone Taxonomy全体を取り込む
  • 必要な分類群だけを部分的に取り込む

採用した方法#

候補表示ではGBIF APIを利用し、検索・分類階層の参照用としてGBIF Backbone Taxonomy全体をRDFへ変換してFusekiへ投入します。

採用理由#

外部APIの応答や制限に依存せず、SPARQLで分類関係をたどれます。

欠点#

約20GB規模のRDF生成・検証・投入に時間とストレージが必要です。

今後の改善#

差分更新、投入処理の再現性、分類データのバージョン管理を整備します。

星型モデルからコンポーネント型へ変更した理由#

課題#

すべての項目をOccurrence直下へ置く星型モデルでは、同定、イベント、位置情報の意味的なまとまりが不明確になります。

候補#

  • すべての述語をOccurrence直下に保存する
  • Identification、Event、Locationを中間ノードとして分離する

採用した方法#

Occurrenceから hasIdentification、hasEvent、hasLocation を介して各コンポーネントを関連付けます。

採用理由#

記録の事実、同定結果、採集・観察イベント、位置情報を区別でき、将来の複数同定や複数イベントにも拡張しやすくなります。

欠点#

保存・検索・詳細表示で関連ノードをたどる処理が必要になり、データ構造は単純な星型より複雑になります。

今後の改善#

複数のIdentification、Event、Locationを入力・編集できるUIを追加します。

dwcとdwciriをバックエンドで変換する理由#

課題#

同じ意味の項目でも、目的語が文字列かIRIかによって適切なDarwin Core語彙が異なる場合があります。

候補#

  • フロントエンドで目的語の型と語彙を判定する
  • 利用者がURIを直接選び分ける
  • バックエンドで語彙メタデータを参照して正規化する

採用した方法#

フロントエンドはDarwin Coreの項目として入力し、バックエンドが目的語をリテラルまたはIRIとして判定します。語彙メタデータに対応する iriEquivalent または literalEquivalent がある場合だけ、述語を変換します。

採用理由#

利用者の入力負担を減らし、変換規則をバックエンドで一元管理できます。

欠点#

語彙メタデータの整備が必要で、対応関係がない語彙は変換できません。

今後の改善#

語彙メタデータの拡充と、変換結果を利用者が確認できるUIを検討します。

フロント入力をフラット形式にした理由#

課題#

コンポーネント型のRDF構造をそのまま入力UIへ出すと、利用者は保存先ノードを理解して入力する必要があります。

候補#

  • Identification、Event、Locationごとに入力フォームを分ける
  • 述語と目的語のフラットな組み合わせとして入力する

採用した方法#

フロントエンドは項目名と値のフラットな組み合わせを送信し、バックエンドが述語に応じてOccurrence、Identification、Event、Locationへ振り分けます。

採用理由#

利用者は項目の意味に集中でき、保存構造の詳細を意識せずに入力できます。

欠点#

同じ項目でも保存先の違いが画面から見えにくく、複数コンポーネントの入力には限界があります。

今後の改善#

フラット入力を維持しながら、同定・イベント・位置情報のまとまりを明示できる編集UIを検討します。
