# 標本ラベル作成・テンプレート仕様

## 1. 目的

検索結果から標本ラベルを作成し、画面上で実データを確認しながら表示項目・寸法を調整して、A4印刷およびPDF出力できるようにする。

利用者が調整した印刷設定は、将来的に名前付きテンプレートとしてPostgreSQLへ保存し、別端末・別セッションでも再利用できるようにする。

テンプレートは生物学的なOccurrenceデータそのものではなく、利用者固有の画面・印刷設定であるため、Fuseki/RDFではなくPostgreSQLへ保存する。

## 2. 現在の画面構成

検索結果でデータを選択し、「ラベル作成」から統合編集ダイアログを開く。

以前の独立したテンプレート作成画面は統合済みであり、`/label-templates/new`は`/occurrences/search`へリダイレクトする。検索画面の独立した「ラベルテンプレート」リンクも廃止している。

関連コード:

- `frontend/src/components/occurrence-label-preview.tsx`: 設定、プレビュー、PDF、印刷
- `frontend/src/app/occurrences/search/page.tsx`: データ選択とダイアログ起動
- `frontend/src/app/label-templates/new/page.tsx`: 旧URLのリダイレクト

## 3. データ選択

- 閲覧可能なOccurrenceを対象とし、ラベル作成自体には所有者制限を設けない。
- 検索一覧の表示とラベル対象はOccurrence ID単位で重複排除する。
- 1つのOccurrenceにつき生成するラベルは1枚とする。
- ラベル順序は検索レスポンス順とし、チェックした順番ではない。
- 新しい検索を実行すると選択状態を解除する。
- 次ページ取得時も選択状態をリセットするため、ページをまたぐ選択保持は現在未対応である。

## 4. 統合編集画面

左側に設定、右側にプレビュー、下部に出力操作を配置する。小さい画面では設定を上側に移し、設定領域とプレビュー領域をそれぞれスクロール可能にする。

初期表示は「個別ラベル」とし、前後操作で選択データを確認できる。「A4全体」では全ページの配置を確認できる。

寸法や表示項目の変更は個別プレビュー、A4プレビュー、PDFへ同じ設定として反映する。

ブラウザのネイティブ`dialog`を利用し、ダイアログ表示中は背景ページのスクロールを止める。閉じるボタンまたはEscapeで閉じる。PDF生成中は閉じる操作と設定変更を無効にする。

## 5. 設定項目

現在の基本設定は以下とする。

| 設定 | 初期値 | 入力範囲 |
|---|---:|---:|
| 横幅 | 40mm | 20–200mm |
| 縦幅 | 20mm | 15–277mm |
| 文字サイズ | 2.5mm | 1.5–6mm、入力step 0.25 |
| QR表示サイズ | 15mm | 8–50mm |

初期状態で有効な表示項目:

- 学名
- 作成者
- 緯度・経度
- 作成日
- QRコード

常設選択肢として以下も提供する。

- 採集・観察日: `dwc:eventDate`
- 場所: `dwc:locality`

この2項目は初期状態では無効とする。

### 5.1 任意項目

「任意項目を追加」では登録画面と同じ`GET /vocabularies/darwin-core`の候補を利用する。

- 名前順に候補を表示する。
- 項目名・URIを大文字小文字を区別せず部分一致検索できる。
- 候補にない絶対URIの直接指定にも対応する。
- 追加項目は削除できる。
- 既存の常設項目を選んだ場合は、重複追加ではなく対応する項目を有効化する。
- 任意項目だけを選択した状態でも出力可能とする。

選択した任意述語の値をラベルに表示し、項目名そのものは印刷しない。

Event、Location、Identificationなど詳細応答内の中間ノードにある値も対象とする。値がなければ空行や`-`を追加せず省略する。同じ述語に複数値がある場合は重複を除き、応答内の順序で別行として表示する。

リテラルは型・言語タグを外して表示し、IRIはURI文字列として表示する。`eventDate`は期間・部分日付を壊さないよう、保存された値をそのまま表示する。

### 5.2 設定値の検証

- すべての表示項目を無効にした場合は出力不可とする。
- QRを有効にした場合、上下左右の余白を除く内寸に収まらなければ出力不可とする。
- 非数値は設定へ反映しない。
- 入力確定時に許容範囲内へ補正する。
- 印刷用DOMの文字高さを確認し、収まらないラベルがある場合は警告する。
- はみ出し警告があっても利用者が出力を続行することは可能とする。

自動縮小、自由配置、任意HTML、任意CSSは扱わない。

## 6. デフォルトラベル

デフォルトラベルはコードに固定された変更不可のテンプレートとし、PostgreSQLや`localStorage`には保存しない。

### 6.1 描画

- ラベル寸法: 40mm × 20mm
- 背景: 白
- 文字色: 黒
- 枠線: 0.2mm相当
- 内側余白: 1mm
- 文字サイズ: 2.5mm
- QR表示寸法: 15mm × 15mm
- QRコードと文字領域の間隔: 1mm
- QRコード周囲: 白い余白を確保する

QRコード用に専用列を確保し、文字がQRコードの背後へ回り込まないようにする。QRを無効にした場合は文字領域をラベル幅いっぱいまで広げる。

項目名やOccurrence IDは表示しない。

- 学名: 太字。欠落時は行自体を表示しない。
- 作成者: 欠落時は`-`。
- 緯度・経度: 両方がある場合のみ表示する。
- 作成日: 欠落時は`-`。
- 日付: `ja-JP`の日付形式。解釈できない値は入力文字列をそのまま表示する。

## 7. Occurrenceデータの取得

学名、作成者ID、作成日時、Occurrence URIは検索結果から受け取る。作成者名は検索画面がユーザーAPIから取得する。

選択データごとに詳細APIを一度取得し、N-Quadsを述語ごとの値一覧として保持する。項目追加・変更時には保持済みの値を使い、詳細APIを再取得しない。

緯度・経度は以下の述語から取得する。

- `http://rs.tdwg.org/dwc/terms/decimalLatitude`
- `http://rs.tdwg.org/dwc/terms/decimalLongitude`

詳細取得失敗は単なる値欠落と区別してエラーを表示し、不完全な状態での出力を無効にする。

## 8. QRコード

QRコードには`occurrence_uri`を格納し、クライアント側で`qrcode`を使って生成する。

生成完了まで出力を無効にする。QR生成に失敗した場合はエラーを表示し、出力を無効のままとする。

## 9. A4配置と出力

A4縦210mm × 297mm、余白は上下10mm・左右5mmとする。使用可能領域は200mm × 277mmである。

テンプレート寸法から配置数を次のように計算する。

- 列数 = `floor(200 / ラベル横幅)`
- 行数 = `floor(277 / ラベル縦幅)`
- 1ページの枚数 = `列数 × 行数`

初期値40mm × 20mmでは5列 × 13行、1ページ65枚となる。超過分は次ページへ配置する。

個別表示中も印刷用A4 DOMを画面外に保持し、個別・A4のどちらの表示状態からでも同じ内容を印刷・PDF出力できるようにする。

PDFは`html2canvas`と`jspdf`で生成する。フォントと画像の読み込みを待った後、画面用の拡大縮小を外し、A4 DOMをscale 2で画像化してPDFへ配置する。

- ダウンロード名: `occurrence-labels.pdf`
- PDFはラスタ画像であり、文字検索・コピーは保証しない。
- 物理印刷寸法はブラウザ、PDF表示ソフト、プリンター側の拡大縮小設定にも依存する。

## 10. テンプレート保存

### 10.1 現在の状態

編集した設定は現在開いているダイアログ内だけで保持する。閉じて開き直すと初期設定に戻る。

以前の`localStorage`への暫定保存は廃止している。既存の`occurrence-web.label-templates`データは読み取りも削除もしない。

名前付き設定を再利用するPostgreSQL永続テンプレート機能は未実装である。

### 10.2 保存方針

利用者テンプレートは`label_templates`テーブルへ保存する。

テンプレートの各設定をPostgreSQLの個別カラムへ分解しない。DB上では、所有者とテンプレートIDを通常カラムで保持し、テンプレート本体は1つの`JSONB`として保存する。

この方針により、文字サイズ、表示項目、任意Darwin Core項目、今後追加する許可済みレイアウト属性が増えても、それだけを理由にDBスキーマ変更を行う必要がないようにする。

DBには任意HTMLや任意CSSを保存しない。テンプレートJSONはアプリケーションが許可した構造化設定だけを保持する。

## 11. PostgreSQLスキーマ

`label_templates`の基本構造は以下とする。

```text
id UUID PRIMARY KEY
user_id UUID NOT NULL REFERENCES users(id)
template JSONB NOT NULL
created_at TIMESTAMPTZ NOT NULL DEFAULT now()
updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
```

`id`はテンプレートIDであり、バックエンドでUUIDを発行する。

`user_id`はログイン利用者からバックエンドで決定し、クライアントが任意の所有者IDを指定できないようにする。

`template`にはテンプレート名を含め、寸法・文字サイズ・QR設定・表示項目などテンプレートを再現するための設定一式を保存する。

所有者単位の一覧取得を行うため、`user_id`にはインデックスを付与する。

利用者削除時の外部キー動作は、既存のユーザー削除方針に合わせる。テンプレート名の重複はDB制約では禁止せず、少なくとも初期実装では同一利用者が同じ名前のテンプレートを複数持てるものとする。

### 11.1 JSONBの基本構造

初期実装では次のような構造を想定する。

```json
{
  "version": 1,
  "name": "採集標本ラベル",
  "widthMm": 40,
  "heightMm": 20,
  "fontSizeMm": 2.5,
  "qr": {
    "enabled": true,
    "sizeMm": 15
  },
  "fields": [
    {
      "type": "builtin",
      "key": "scientificName",
      "enabled": true
    },
    {
      "type": "builtin",
      "key": "creator",
      "enabled": true
    },
    {
      "type": "builtin",
      "key": "coordinates",
      "enabled": true
    },
    {
      "type": "builtin",
      "key": "created",
      "enabled": true
    },
    {
      "type": "darwinCore",
      "uri": "http://rs.tdwg.org/dwc/terms/eventDate",
      "enabled": false
    },
    {
      "type": "darwinCore",
      "uri": "http://rs.tdwg.org/dwc/terms/locality",
      "enabled": false
    }
  ]
}
```

これは保存構造の基準であり、フロントエンド内部のstate名をそのまま無制限に永続化するという意味ではない。API境界で許可したテンプレートDTOへ変換してから保存する。

### 11.2 `version`

テンプレートJSONには整数の`version`を必須で持たせる。初期値は`1`とする。

将来JSON構造を変更する場合は、DBカラム追加ではなく、読み込み時または明示的なデータmigrationで旧versionから新versionへ変換できるようにする。

不明なversionは黙って解釈せず、利用者へ読み込みエラーとして扱う。

### 11.3 JSONBの検証

DBでは少なくとも`template`がJSON objectであることを保証する。詳細な意味検証はservice層で行う。

serviceでは少なくとも以下を検証する。

- `version`が対応済みであること
- `name`が空でなく、最大長以内であること
- 横幅、縦幅、文字サイズ、QR寸法が有限の数値で許容範囲内であること
- QRを有効にした場合にラベル内へ収まること
- `fields`が配列で、許可された構造だけを含むこと
- builtin項目の`key`が許可済みであること
- 任意述語が許可されたURI形式であること
- 表示項目が1つ以上有効であること
- 任意HTML、JavaScript、CSSなど実行可能な内容をテンプレートとして受け入れないこと

## 12. APIと認可

ログイン済み利用者だけが自分のテンプレートを操作できるようにする。

予定API:

- `POST /label-templates`: テンプレート作成
- `GET /label-templates`: 自分のテンプレート一覧取得
- `GET /label-templates/{id}`: 自分のテンプレート取得
- `PUT /label-templates/{id}`: 自分のテンプレート更新
- `DELETE /label-templates/{id}`: 自分のテンプレート削除

認可:

- 未ログイン: `401 Unauthorized`
- 自分のテンプレート: 操作可能
- 存在しないテンプレート: `404 Not Found`
- 他人のテンプレート: 存在を通知しないため`404 Not Found`

作成時の`user_id`と`id`はサーバー側で決定する。更新APIでも所有者を変更できないようにする。

APIで返すテンプレートは、少なくとも`id`とテンプレート本体を含む。所有者IDをフロントエンド処理に必要としない場合は、レスポンスへ常に露出させる必要はない。

API追加時はOpenAPIと`spec/11_api_contract.md`も更新する。

## 13. テンプレート適用

保存したテンプレートをラベル作成で使うため、統合編集ダイアログへ次の操作を追加する。

- デフォルトテンプレートまたは自分の保存済みテンプレートを選択する。
- 現在の設定を名前付きテンプレートとして保存する。
- 保存済みテンプレートを更新する。
- 不要なテンプレートを削除する。

独立したサンプル編集画面へ戻さず、実データを使う現在の統合編集画面上で保存・選択を完結させる。

A4、個別、PDF、印刷は同じテンプレート定義を使う共通描画処理を利用し、画面ごとに設定解釈が分岐しないようにする。

## 14. 実装順序

1. **完了**: 検索結果とラベル対象をOccurrence ID単位で重複排除する。
2. `label_templates`のPostgreSQL migrationを追加する。
3. JSONB用DTO、repository、serviceを追加する。
4. serviceにJSON構造・値のvalidationを追加する。
5. handler、route、認可、OpenAPIを追加する。
6. 統合編集ダイアログへ保存・選択・更新・削除UIを追加する。
7. デフォルトテンプレートと利用者テンプレートの描画処理を共通化する。
8. 保存した寸法に応じたA4配置を回帰確認する。

## 15. テスト要件

バックエンドテストを追加する場合は、必ずテストコードより先に`backend/test.md`へテスト内容を追記する。

### 15.1 migration / repository

- migration適用で`label_templates`が作成されること
- `id`がテンプレートの主キーとして機能すること
- `user_id`が既存利用者を参照すること
- `template`へJSON objectを保存・取得できること
- 小数の寸法・文字サイズをJSONB内で欠落なく保持できること
- 任意Darwin Core項目を含むテンプレートを往復保存できること
- 所有者条件を付けた一覧・単体取得・更新・削除が正しく機能すること

### 15.2 service / handler

- 正常なテンプレートを作成、一覧取得、単体取得、更新、削除できること
- 未対応の`version`を拒否すること
- 名前、寸法、文字サイズ、QR寸法、表示項目のvalidationが機能すること
- 不正なJSON構造を拒否すること
- 他ユーザーのテンプレートを取得・更新・削除できないこと
- 未ログインが`401`になること
- 他ユーザーまたは存在しないIDが`404`になること

### 15.3 フロントエンド

- 検索結果の一括選択・個別選択と選択件数が一致すること
- 重複した検索行からラベルが重複生成されないこと
- 初期サイズで65件・66件のページ分割が正しいこと
- 個別表示の前後移動が正しいこと
- 学名欠落、作成者欠落、座標片側欠落、日付欠落時の表示が仕様通りであること
- QRコードがOccurrence URIを格納すること
- 保存済みテンプレートを選択すると個別、A4、PDFへ同じ設定が反映されること
- テンプレート寸法に応じてA4配置数が変わること
- 任意Darwin Core項目を保存後に再読込して同じ項目が表示されること
- PDFが選択件数分のラベルを含むこと

## 16. 完成条件

固定デフォルトラベルについては、検索結果からのラベル作成、個別・A4プレビュー、PDFダウンロード、印刷までを試用可能な状態とする。

永続テンプレート機能は、次がすべて揃った時点で完成と扱う。

- PostgreSQL JSONB永続化
- ユーザー所有権
- CRUD API
- JSON versionとvalidation
- 統合編集画面からの保存・選択・更新・削除
- 保存テンプレートの個別・A4・PDF・印刷への適用
- 最低限のバックエンドおよびフロントエンド回帰テスト
